## Things that change the compiled JavaScript (the main agent compares dist-server with a baseline)
Only require lines and comments may differ in the compiled file. So:
- `import x = require('...')` and `export = ...` only. No `import x from`, no `export const`, no `export default`,
  no enum, no namespace with values, no parameter properties, no decorators. `import type {...} from '...'` is fine
  (erased).
- Class fields: `declare field: T` (a plain field becomes a real field under ES2022 and changes behaviour).
- `export =` moves `module.exports = ...` to the END of the compiled file. That is safe only when nothing but
  function declarations follows it in the source AND the file is not part of a require cycle. Check both.
- A file that sets `module.exports.name = value` several times: follow the converted precedents (requestUtils.ts,
  parsers/parseNfoMetadata.ts): the functions keep their bodies and the file ends with one `export = { a, b }` that
  has exactly the same keys. Say in your report how you did it for each such file; if a value can only be exported
  by changing its code, restore the file and report.
- The code has no semicolons: a line that starts with `(` or `[` or a cast continues the previous statement.

## Typedefs that other files import (important in this run)
Some already-converted TypeScript files use a JSDoc typedef of a file in the sets as a REAL type, for example
`type RssPodcastEpisode = import('../utils/podcastUtils').RssPodcastEpisode`. Files of other sets do the same from
JSDoc. Rule for every set: a typedef of your file that any other file references (your set brief lists them) must
stay available under the SAME NAME as a type of the module after the conversion. The precedent is
server/managers/LogManager.ts line 14: a type-only `declare namespace X { ... }` merged with the exported class,
with a one-line comment. For a file that exports an object, the main agent tested that this compiles and emits
only one extra local const:
    const a = { parse }
    declare namespace a { type Result = { value: string } }
    export = a
Use this form only where a typedef must stay importable; say so in your report (it adds one local const to the
compiled file). In your own TypeScript files, refer to a typedef of another file with
`type Name = import('../path/File').Name`; it resolves while that file is JavaScript and also after its owner
converts it by this rule.

## 10. CLAUDE.md and the brief: wrong, unclear or missing

1. No rule covers a call that the compiler rejects for its argument count (TS2554, `replace(publishedYear)`). Allowance 1 covers only TS2367. I used a local intersection type (section 1, adjustment 3). If you do not accept it, AudioFileScanner cannot be converted without a code change.
2. No rule covers `filter(Boolean)` and `filter((x) => x)`, which do not remove null from the element type. For `Boolean` I used a file-local declaration like the isNaN precedent. For the arrow callback nothing cast-free exists. I recommend a ruling that allows one cast with a comment at AudioFileScanner.ts line 258 (`as AudioFile[]`), so that the return type becomes `Promise<AudioFile[]>` again. Otherwise BookScanner and PodcastScanner cannot be converted without `!` at every use.
3. CLAUDE.md does not say what to do with a require that is used only in JSDoc types. `import x = require()` is then removed from the compiled file (section 8). The express rule covers only the destructured case.
4. The `!` cases F, A and L do not say whether the guarantee may be in another file (a caller that loads the association, or TaskManager that sets Task.data). LibraryScanner has both.
5. `!` does not remove false. A result typed `false | {...}` that the code reads without a test (LibraryScanner js:344) has no allowed form, so that file cannot be converted under the current rules.
6. A file of another set can be `.ts` in one check and `.js` in the next (MediaProbeData, and probably parseNameString). One check is not conclusive while the others work: errors appeared and disappeared in my file without a change of mine.
7. In a TypeScript importer, a JSDoc `@returns {Object}` of a JavaScript file is the type `Object`, not any (TS2696 when I annotated probeAudioFile() as `Promise<unknown>`). I left the return type of probeAudioFile() to inference.
8. The task asks for set3/report.md, but the Write tool refuses report files from a sub-agent. The report exists only as this message.
