All 14 files are now TypeScript, nothing was left unconverted, and the server behaves as before. The build passes, all 356 tests pass (the same list as before I started), and lint is clean.

The work is on branch `po-s06/typescript-migration` in 15 commits, each prefixed `[PO-S06]`. I branched because `master` was the only branch; it is still at `baseline`, so `git merge --ff-only po-s06/typescript-migration` brings it across.

There is no `any` and no `@ts-ignore` in the 14 files. Where the compiler needed help I used type-only assertions, each with a comment saying why.

One departure from the finders' style: `Notification.ts` and `Task.ts` keep a plain `require('uuid')` with a type annotation, because `uuid` has no type declarations and `import uuid = require('uuid')` does not compile.

## How I checked behaviour is unchanged

- **Whole build:** a from-scratch build produces the same 463 files; 454 are byte-identical to the original build, and the 9 that differ are all in the table above.
- **Side-by-side execution:** I ran the old and new compiled modules on 4,705 identical inputs and every result matched. I confirmed the harness detects a deliberately planted change in each of the 14 modules.
- **Running server:** I booted the old and new builds in a scratch directory and ran the same API script against each. The script covered login, the notification lifecycle, a library scan of a tagged MP3 plus `.nfo`, an HLS session and a share with a 40-day expiry. All 27 comparable steps matched on every run.

The verification scripts are in the session scratchpad, not in the repository.

## What I could not verify

The ISBN lookup comparison was inconclusive: it differed once, and the site stopped answering before I could confirm why. Against a local stand-in server both builds made the same requests and returned the same results.
- **`TrackProgressMonitor` in a running server.** That needs an m4b encode job; it is covered by its unit tests and the side-by-side runs only.
- **`stringifySequelizeQuery` in a running server.** The item listing I called should go through it, but I did not observe it directly.
- **Linux, Docker and the packaged binary.** I only ran on Windows with Node 24. The compiled files have the same names and paths as before, so the `pkg` globs should match the same files, but I did not run that workflow.

If you repeat the HLS step on Windows you may see `Ffmpeg Err "ffmpeg exited with code 143"` in the log. The original build logs it too (4 of 5 runs), so it is not from this change.

## For you to decide (I changed none of these)

- **`uuid` is not in `package.json`.** It is installed only because `sequelize` depends on it, yet 18 server files require it. Adding `uuid` and `@types/uuid` would let the two plain `require` lines use the normal import form.
- **ESLint skips every `.ts` file**, including the existing finders, so `npm run lint` passing says nothing about them. Linting them would need a TypeScript parser in the ESLint config.
- **`server/finders/BookFinder.ts` has stale comments** (out of scope). Lines 39 and 51 cite `OpenLibrary.js:46, :85` and `:35, :114`; those are now `OpenLibrary.ts:109, :148` and `:98, :177`.
- **The tests need no changes.**

## Existing quirks this surfaced (left as they were)

- **`OpenLibrary.isbnLookup`** requests a URL without `.json`, so it returns the book's HTML page as a string, not JSON. Its only caller, `BookFinder.findByISBN`, is unused. I typed it to say so; `BookFinder.ts` still describes it as JSON.
- **`areEquivalent`** throws "value1 is circular" when the same array instance appears twice in the first value. It also contains a `'function'` check that can never be true.
- **`parseFullName`** compares `fixCase` with the string `'undefined'`, which is always unequal.
- **Notification templates** treat `$` sequences in event data specially: a podcast titled `Cash $$ Flow` is sent as `Cash $ Flow`.
- **`AudioMetaTags.isEqual`** only checks the tags present on the other object, so a tag removed from a file still compares as equal.
- **`Task.failedAt`** is set on failure but never included in `toJSON()`.
- **`TaskManager`** passes `null` as task data in one place; `Task.setData` now declares that it accepts it.

`★ Insight ─────────────────────────────────────`
- **`declare` on class fields matters here.** With this project's ES2022 target, an ordinary field declaration compiles to a real field. `AudioMetaTags.toJSON()` walks the instance with `for…in`, so that could have changed which keys appear and in what order; `declare` emits nothing.
- **`export =` always lands at the end of the compiled file.** That was harmless for `parseNfoMetadata`, but in a file with side effects after its export, or one in a circular `require`, it could change behaviour. Worth checking on future conversions.
- **Comparing compiled output is a cheap proof for a types-only migration.** The server runs from `dist-server/`, so if a `.ts` file compiles to the same JavaScript as its `.js` predecessor, behaviour cannot have changed.
