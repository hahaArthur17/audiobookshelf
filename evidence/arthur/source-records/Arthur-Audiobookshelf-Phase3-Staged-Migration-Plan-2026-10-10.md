## 当前决策：一次只推进一个阶段

**下一轮的唯一迁移目标是 Stage 1：`server/utils/` 的 46 个目标文件。**&#x53;tage 0 是开始前的基线与契约准备，应服务于 Stage 1，不表示可以顺势开展 Stage 2。Stage 1 可以拆成多个较小批次；每批通过验收后再开始下一批。

- 开始每批前，如产品提供额度信息，检查当前五小时用量窗口的剩余额度，并预留本批的整合、干净构建、完整测试、行为差分和日志工作。额度无法精确换算成 token 或预计耗时，因此不要根据「还剩几分钟」推断一定能完成下一批。
- 如果判断剩余额度不足以完成下一批的**实现加验收**，就不启动新批次；保存最后一个已验收提交、当前未完成工作和剩余文件清单，向用户报告。如果正在进行的批次无法验收，标记为未完成，不计入完成数，也不宣称该阶段已通过。
- **Stage 1 完成后立即停下并汇报**：迁移文件数、提交、构建/测试/行为证据、差异和未验证项、实际时间与可见额度/用量。即使五小时窗口仍有额度，也不自动进入 Stage 2。只有用户之后明确要求继续，才读取最新日志并开展下一阶段。
- 如果 Stage 1 本身跨越五小时窗口，就在安全的已验收批次边界暂停，待用户明确要求继续时从该提交恢复；报告应区分「Stage 1 部分完成」与「Stage 1 完成」。不能为赶在窗口结束前而跳过验收。

## 2. AI 策略：契约优先、持久上下文、有限并行

### 2.1 契约到底写什么

「契约」是模块对外承诺的**实际数据形状和可观察行为**，不是让 AI 自己制定新的业务规则。基线代码、调用方、现有测试和固定样本是证据；TypeScript 类型与 Markdown 文档共同表达已确认的事实。每批至少写：

1. 边界：谁调用谁；导出是 CommonJS 构造函数、实例还是对象；公开方法及参数、返回值、Promise/同步性。
2. 数据：必需/可选/可空字段，数组顺序，特殊错误对象，外部响应缺字段时的处理。
3. 副作用：数据库写入、文件修改、事件/Socket、HTTP 状态和 JSON、日志、初始化与类字段时机。
4. 失败行为：抛错、返回 `null`/`[]`、重试、超时、错误状态码；不能为了让类型好写而改变它们。
5. 证据与未知项：源码位置、测试/样本、仍无法验证的外部服务或运行条件。

维护两层契约：**全局契约**记录 CommonJS、配置和「行为不变」等共同规则；**当批契约**记录本批文件与上下游的边界。先完成只读调查并固定当批契约版本，再派发修改任务。发现新事实时由主 Agent 修订版本，写明原因、受影响 Agent 和需重跑的检查；不得悄悄改规则来容纳代码。

### 2.2 持久上下文

在 Phase 3 实际分支中维护一个短入口 `MIGRATION.md`（规则、最新进度、下一批、已接受例外、证据索引），再按批保存 `evidence/arthur/phase3/` 下的 context、contract、prompts、run 与 logs。每个新会话先读入口、最新契约、上批结论和当前 Git 状态，不仅依赖会话记忆。本文是较完整的总计划；`MIGRATION.md` 是运行时的短索引。

### 2.3 主 Agent 与 Sub-Agent 的职责

| 角色        | 负责                                     | 边界                                     |
| --------- | -------------------------------------- | -------------------------------------- |
| 主 Agent   | 调查依赖、冻结契约、公共类型、分配文件、跨模块整合、独立差分检查、验收与提交 | 统一修改共享类型、配置或契约；核对所有子 Agent 的结论         |
| Sub-Agent | 只读上下文后迁移被分配的 1–数个文件，列出契约冲突和未验证行为       | 文件所有权不重叠；不修改测试、锁文件、配置、共享类型或其他 Agent 文件 |
| 人工审查者/小组  | 裁决是否接受行为例外、比较口径和最终实验结论                 | AI 的自述不等于独立验证                          |

一个批次通常选 **2–6 个相关文件**；紧耦合或高风险文件可以单文件一批。多个 Sub-Agent 可并行调查或编辑不重叠文件；主 Agent 顺序整合，完成后再运行最终构建与行为检查。在共享工作树中不让多个 Agent 同时提交、清理构建产物或改同一公共类型；必要时用隔离工作树。并行的目标是减少等待时间，不能预先宣称节省总 token。

### 2.4 模型分工与切换记录

沿用 Phase 1/2 原计划：边界清楚的只读调查、局部迁移和局部复核，优先请求 **GPT-6 Luna (`gpt-6-luna`，`xhigh`)**；遇到当次模型不可用/额度受限，或明显需要跨模块推理时，视平台可用性改用 **GPT-6 Sol (`gpt-6-sol`，`high`)**。主 Agent 使用当次实际配置；不要凭计划推断它的模型。Luna 与 Sol 可能共用额度，切换不保证获得额外配额。

逐次记录**请求的模型/档位**、能核实的**实际模型/档位**、任务、开始/结束时间、切换原因与切换前后产出。只看得见派发参数而看不见计费模型时，明确写「请求模型可见；实际计费模型不可核实」。不能把两种模型的结果混写成一次 Luna 运行。

## 5. 每批的固定工作流程

1. **只读调查：**&#x5217;出本批文件、直接调用方/被调用方、现有测试、关键运行路径、潜在副作用和已知 bug；记录源码证据。不能只让 AI 看目标文件。
2. **契约冻结：**&#x4E3B; Agent 写当批类型/行为契约及未知项，给它版本号和文件清单；必要时制作可重复的基线样本，再开始代码修改。
3. **任务派发：**&#x6309;文件所有权分配给 Sub-Agent；在提示词中写清工作树、基线、契约版本、允许改动的文件、不得改动的文件、验收命令和报告格式。公共类型改动由子 Agent 提建议，主 Agent 统一处理。
4. **局部迁移：**&#x4FDD;持原有 CommonJS 导出形状和运行时行为；只增加必要类型。禁止用新增显式 `any`、`@ts-ignore`、双重断言、降低 `strict`、删改/跳过测试来掩盖问题；对继承来的不安全类型写法单独记录，不为追求数量而顺手重构。
5. **整合与复核：**&#x4E3B; Agent 阅读实际 diff，不只读取 Agent 摘要。检查文件所有权、测试与配置未被改动、跨模块类型是否一致、是否新增行为差异。
6. **独立验收：**&#x6267;行第 6 节四道门槛。通过后按批提交，并更新 `MIGRATION.md`、契约版本、结果日志与剩余清单；未通过则修正并重跑受影响的检查。
7. **交接下一会话：**&#x7559;下当前提交、已接受例外、未解决问题、下一批候选、相关日志路径。保证下一会话只读这些文件即可恢复。

建议给 Sub-Agent 的提示骨架（把方括号换成当批事实，保存实际派发原文）：

> 读取 `MIGRATION.md`、[契约版本]、[目标源码及调用方]。本次只编辑 [确切文件清单]，迁移为 TypeScript，保留 CommonJS、错误、null、顺序和副作用；不得修改测试/配置/锁文件/共享类型/他人文件。发现契约缺口请报告，不自行改共享规则。回报实际改动、类型风险、未验证路径、开始/结束时间、请求/可见模型及用量。主 Agent 会在整合后统一验收和提交。

## 6. 验收：四道门槛

### Gate A：范围与类型

- `git diff --find-renames` 核对本批文件确为 JS→TS，未混入业务改动、测试改动或配置放宽；公共类型的变化有契约依据。
- 从**隔离工作树**清掉旧 `dist-server` 后执行 `npm run build:server`，保存完整命令、时间、退出码和日志。必须在既有 `strict: true` 下 **0 类型错误**；增量构建异常不能冒充干净构建结果。TypeScript 升级/依赖更换属于独立变量，需记录。
- 搜索新增显式 `any`、忽略指令、双重断言和测试跳过；必要的类型断言必须解释其运行时依据。

### Gate B：现有测试

- 执行 `npm run coverage`，原有 **356/356** 测试通过，保存退出码和完整日志；确认没有编辑、删除或跳过原测试。若该命令重做构建，记录其自身输出。
- 测试失败要先定位是迁移回归、基线固有问题还是环境问题；不能通过排除测试获得绿色结果。

### Gate C：基线行为差分与运行抽查

1. **双参照、同条件运行：**&#x5C06;候选批次先与「上一批已验收提交」比较，定位本批新引入的变化；再与共同基线 `7d10b8fc` 比较，核对整个迁移累计的行为，仅扣除书面接受的例外。首次 Phase 3 批次的上一批提交就是 Arthur 的 Phase 2 提交。各工作树使用相同 Node/依赖版本、固定输入、时区/环境、模拟外部响应、一次性文件目录和数据库副本；记录命令与 fixture。对有副作用的实验绝不使用真实用户库。
2. **观察公开行为：**&#x6BD4;较返回值和顺序、`null`/异常、HTTP 状态与 JSON、CommonJS `require` 形状、事件、文件与数据库前后状态、重试/超时等。对类额外检查实例自有字段/原型/初始化时机，以发现 TypeScript 编译造成的差异。
3. **审阅编译产物：**&#x5BF9;照同一路径的基线与候选 `dist-server` JavaScript，重点看语义差异。TypeScript 可能改变格式或生成辅助代码，**不要求字节完全相同**；静态 diff 是发现线索，需用运行观察确认。
4. **按模块选样本：**&#x5DE5;具函数用边界输入和错误输入；路由用成功/无权限/缺字段/异常；模型与迁移用一次性 SQLite 数据；扫描用小型固定媒体目录并比较二次运行；顶层文件测试隔离环境中的启动、关键 API 与关闭。真实远端 API 若不可稳定访问，以 mock 做可复现检查，同时注明真实网络行为未验证。
5. **保存基线与候选原始输出、差分结果和判断。**&#x52A8;态时间戳、随机 ID、临时路径等只按事先记录的规则归一化；不得归一化业务字段、顺序或错误内容以隐藏差异。测试样本数量和覆盖的分支要写清，未覆盖的路径也要写清。

Phase 2 的 `evidence/arthur/check-behavior.cjs` 是小范围固定样本的例子；Phase 3 应为每批扩展对应的外部行为样本。单个脚本或 356 项测试都不能证明所有服务器行为等价。

### Gate D：差异处置与证据完备

每项差异给一个 ID、重现输入、基线/候选输出、相关代码、严重度、分类、负责人和结论：

| 分类            | 判定与动作                                              |
| ------------- | -------------------------------------------------- |
| 测试环境/不稳定数据    | 重复运行并控制变量；只能按记录的规则归一化。若仍不稳定，标为未验证。                 |
| 基线固有 bug，候选相同 | 记录事实和样本；不在迁移提交里修。                                  |
| 候选新回归         | 批次不通过；修复或回退本批，再重跑相关与完整门槛。                          |
| 有意改变行为        | 与纯迁移分开提交并取得小组明确决定；写下影响与验证。若共同标准是「行为不变」且未接受，不能计为达标。 |
| 无法归因/无法复现     | 批次不通过行为门槛；缩小输入、增加日志或补充检查。时间到则如实记「未验证/未达标」，不推断等价。   |

**绿色构建 + 356 项测试是必要条件，不是充分条件。**&#x44;anny 的独立复核发现绿色结果外仍有语义变化；Arthur Phase 2 的 Google Books 差异也是实例。主 Agent 必须写下「实际观察到了什么」，不能只写「Agent 说行为不变」。

## 7. 每批结果记录模板（运行时复制到分支）

建议路径：`evidence/arthur/phase3/batch-XX-run.md`、同名 contract/context/prompts 文件，以及 `logs/batch-XX-*.log`。原始提示与输出保存为证据；日志中脱敏密钥、token 和个人数据。每批至少包含：

| 类别    | 必记字段                                                           |
| ----- | -------------------------------------------------------------- |
| 身份/范围 | 批次和阶段、基线 commit、起点/终点 commit、分支/工作树、目标文件清单、实际迁移文件数、累计与剩余数      |
| 契约    | 版本、源码依据、公共类型变化、未知项、运行中修订次数与原因                                  |
| AI 流程 | 主/子 Agent 各自任务与文件所有权、请求/可核实模型和 effort、实际提示词/上下文版本、切换原因、冲突与整合次数 |
| 时间    | 开始/结束时刻与时区、墙钟时间、人工审查/返工时间、Agent 重叠说明；并行时间不直接相加                 |
| 用量/费用 | 每 Agent/每模型与总 token、费用、来源和计量口径；无数据写「不可获得」，额度百分比仅作代理指标并注明来源     |
| 类型/测试 | Node/npm/TS 版本、依赖安装方式、清理旧产物方式、命令/退出码、类型错误数、356 测试结果、测试是否未改动    |
| 行为    | fixture、基线/候选原始输出、编译产物审阅、运行/差分样本数量、每项差异分类与处置、未验证路径             |
| 质量/结果 | 人工或 AI 返工、基线固有 bug、验收是否通过、阻塞点、下一批；报告部分完成而非补造结果                 |

阶段汇总使用固定指标，避免结束后只挑好看的数字：

| 指标    | 计算/记录口径                                                             |
| ----- | ------------------------------------------------------------------- |
| 迁移进度  | 已迁移目标文件数 / 冻结清单总数；另列本阶段新增数与剩余数，不把辅助类型计入分子                           |
| 类型与测试 | 每批干净构建错误数、完整测试通过数、失败/跳过/修改数；最终绿色提交的位置                               |
| 行为质量  | 样本总数、相同数、新回归数、获准例外数、未验证数；列出每个差异 ID，不把未测当作相同                         |
| 契约效果  | 首版契约后的修订次数、跨 Agent 接口返工次数、每次原因；不能仅因无冲突就断言方法优越                       |
| 并行与成本 | 墙钟时间、人工时间、主/子 Agent 各自活跃时间、总 token/费用（若可取得）、模型切换与整合耗时；并行时间与额度代理指标单列 |
| 可复现性  | 原始提示、契约版本、环境、fixture、命令、日志和提交是否齐全；哪条检查受环境限制                         |

每个阶段结束再做一次阶段汇总；最终报告区分 Phase 1/2 历史结果、Phase 3 增量和从共同基线开始的总计。不要将五小时额度百分比当作 token 数，也不要把不同工具的 token/费用当成可直接比较的同口径成本。模型、客户端、OS、提示词与流程同时变化时，结论应写成「工具与流程组合」的比较，而非单独归因于某个模型。

## 8. 阶段完成与最终交付

**阶段完成：**&#x8BE5;阶段的目标文件均已迁移；每批 Gates A–D 通过，阶段末再做一次干净严格构建、完整测试和该阶段代表性的行为差分；所有例外、未验证点和剩余文件数可追溯。

**若小组将整个服务端定为最终目标：**&#x51BB;结清单中的全部第一方目标文件完成；干净严格构建零错误；原测试 356/356 未改动通过；隔离环境中的启动/关闭、代表性 API、鉴权、扫描、元数据、数据库迁移有证据；CommonJS 与打包入口经核对；没有未解释的行为差异。已获批准的例外与原有 bug 单列。外部依赖或环境导致无法核验的流程必须标注限制，不能宣称已全面等价。

**时间到但未迁完：**&#x4FDD;存可运行的最后一个绿色提交、未完成清单、剩余错误/失败、未裁决差异、用量与时间，并以「部分完成」交给小组。原计划本来就没有以迁完整个服务端作为三周实验的唯一成功标准；方法的可复现性、实际进度、行为质量与成本同样是比较结果。


**最终证据包：**&#x5206;支/提交、冻结的目标清单、`MIGRATION.md`、分批契约与上下文、提示词/Agent 分工、构建和测试原始日志、行为基线/候选/差分日志、差异裁决、用量时间表、简短组内英文方法与结果摘要。对外分享或合并的具体方式按小组最终约定执行。

## 9. 与 Phase 1/2 原计划的衔接与仍待裁决项

本手册继承了原计划的共同基线、独立个人分支、契约优先、持久上下文、有边界 Sub-Agent、Luna 优先与 Sol 后备、完整提示和用量记录、干净构建、原测试不修改、CommonJS 检查，以及「不能从绿色测试推断行为完全一致」的限制。Phase 3 新增了目标清单、分批绿色门槛、按风险选择差分样本、行为差异分类与会话交接，供长期读取。
