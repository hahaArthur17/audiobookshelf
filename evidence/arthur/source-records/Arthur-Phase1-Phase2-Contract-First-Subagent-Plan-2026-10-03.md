## 一、我的方法究竟是什么

我采用 **方法 4：契约优先 + 持久上下文 + 有边界的 Sub-Agent**。这里的“共享契约”指 `Finder → Provider → Controller` 等模块之间共同遵守的数据类型和运行时行为，不只是写一份笼统的 Markdown 规则，也不等于全组四个人必须采用同一套实现。

1. **先调查接口，再写契约。**&#x8BA9; Codex 只读目标代码、调用方和现有测试，列出输入、输出、错误、可空字段、异步行为、CommonJS 导出方式及不确定点。把结论写成短的上下文文档；关键约束最终要落实到 TypeScript 类型或可核对的行为检查中。
2. **固定给 Agent 的上下文。**&#x5728;个人分支中保存简洁的 `evidence/arthur/phaseX-context.md` 和 `phaseX-contract.md`：基线、目标文件、已知坑、契约、边界、验收命令和当前发现。后续对话与 Sub-Agent 都引用同一版本，修改时记录原因。
3. **按契约分配互不重叠的文件。**&#x4E3B; Agent 负责契约、公共类型、协调和最终检查；Sub-Agent 只编辑明确分给它的文件，并报告与契约冲突之处。若工具让多个 Agent 共用同一工作树或 Git index，应使用隔离工作树，或至少严格限定文件所有权并由主 Agent 顺序提交。
4. **用证据检验方法。**&#x8BB0;录主 Agent 与所有 Sub-Agent 的 token/费用总和、实际用时和人工返工。并行可能缩短墙钟时间，但可能增加总 token 和集成成本，不能预先宣称“更省”。
5. **明确子 Agent 的模型分工。**&#x8FB9;界清楚的代码调查、单文件迁移和局部复核，优先尝试 **GPT-6 Luna（`gpt-6-luna`，Extra High／`xhigh`）**。遇到该模型当次不可用、额度受限，或契约冲突需要更强的跨模块推理时，若平台允许，改用 **GPT-6 Sol（`gpt-6-sol`，High／`high`）**。切换前后分别记录承担的任务、原因、token、费用、用时和产出；不能把两种模型的结果混记成一次“Luna 运行”。不同模型可能共用额度，因此切换是否可用以当时平台显示为准。

**与其他人的区别要写清楚：**&#x41;ung 已试过“先写规格和计划”以及并行 Sub-Agent，单独使用这两件工具不构成独特方法。我的实验重点应是**先明确跨模块的类型与行为契约，让多个 Agent 都依据同一契约工作，再核查契约是否降低接口返工和运行时回归**。如实际执行与此不同，报告按真实过程描述，不事后美化。

- [ ] **只读摸底。**&#x67E5;看三个 Finder、它们使用的 Provider、直接调用方，以及 `test/server/finders/BookFinder.test.js`。让 Codex 产出接口图和风险清单；此时不改代码。
- [ ] **写契约。**&#x660E;确三个 Finder 的公开方法、参数/返回值、异常与缺失字段处理、现有 `module.exports` 实例导出形状、JS 调用方的加载方式。让 Codex 标出代码证据和未知项；我审阅后固定文档版本。
- [ ] **落实类型并分工。**&#x4E3B; Agent 管理公共类型和契约；Sub-Agent A 负责 `BookFinder`，Sub-Agent B 负责 `AuthorFinder` 与 `PodcastFinder`。子 Agent 的局部任务优先使用 GPT-6 Luna `xhigh`，遇到上述切换条件再使用 GPT-6 Sol `high`。所有人只改各自负责的目标文件；需要改公共类型时先向主 Agent 提出，不并发改同一文件。
- [ ] **主 Agent 整合。**&#x68C0;查类型是否表达真实输入/输出，是否通过 `any`、`@ts-ignore`、双重断言或删除/跳过测试掩盖问题；核对 JS 调用端和编译产物的 CommonJS 兼容性。
- [ ] **保存阶段结果。**&#x8BB0;录干净构建、相关测试和完整的 `npm run coverage` 结果；若能用固定输入验证搜索结果与原版本一致，也保存差异与限制。提交代码和上下文、提示词、用量、检查日志。

3. *执行提示：*“按已确认的契约迁移分配给你的文件；不得修改测试或他人的文件。报告新增类型、遇到的契约冲突、改动文件和未验证行为。”

## 四、Phase 2：同一条元数据流程的跨模块迁移

**共同任务范围：**&#x50;hase 1 的 3 个 Finder、`server/providers/` 下 9 个 JS 文件，以及 `server/controllers/SearchController.js`，共 **13 个第一方文件**。按原小组安排，从固定基线另开实验分支；我的建议限时约 **8 小时**。这轮比较的是跨模块契约是否真正帮助迁移，而非只把 Phase 1 文件再命名一次。

- [ ] **重新确认共同输入。**&#x4ECE; `7d10b8fc` 起步，保留小组一致的任务描述和验收条件；在个人分支重新建立/修订 Phase 2 契约，不把其他成员的代码或自己的 Phase 1 实现直接搬入。
- [ ] **扩展契约。**&#x91CD;点写 Provider 返回数据如何进入 Finder，再如何进入搜索 API；标明外部响应缺字段、超时/错误、不同搜索来源、可选字段、状态码及 CommonJS 调用边界。契约应约束实际代码，而非只作说明。
- [ ] **分配文件所有权。**&#x4E3B; Agent 管理契约、公共类型、三个 Finder、`SearchController` 和最终整合；Sub-Agent A 处理约定的一组 Provider，Sub-Agent B 处理其余 Provider。子 Agent 同样优先使用 GPT-6 Luna `xhigh`；跨模块难点或额度受限时，按已记录的条件切换至 GPT-6 Sol `high`。具体拆分先依据依赖图确定，两个 Agent 不同时改公共类型、配置、锁文件或测试。
- [ ] **分段检查与合并。**&#x5404; Sub-Agent 提交修改摘要和不确定点；主 Agent 对照契约整合并运行干净构建、完整测试、编译后导出/结果形状检查及可执行的 API 行为抽查。记录未覆盖的外部 Provider 情况，不把 356 项测试通过等同于行为完全一致。
- [ ] **交付用于组内比较。**&#x63A8;送个人实验分支，分享提交或 PR 链接及完整日志。比较前保持独立成果；最后由小组选一个版本作为最终代码状态。

## 五、验收与比较：每次都留得下证据

| 项目    | 我的记录方式                                                            |
| ----- | ----------------------------------------------------------------- |
| 代码进度  | 从共同基线到本分支的改动文件、JS→TS 文件数、未完成文件和提交链接；不把其他人的进度算作我的成果。               |
| 类型与构建 | `strict` 下的 `tsc` 错误数、是否从空的 `dist-server` 生成物构建、公共类型质量以及任何逃逸类型写法。 |
| 测试与行为 | 原有测试通过数、是否修改/跳过测试、CommonJS 消费方式、固定样本或 API 响应的差异与已知盲点。             |
| 效率与成本 | 墙钟时间、本人实际工作时间、按 Agent 和模型分别记录的用量及总计、费用口径、模型切换原因、返工次数和集成冲突。        |
| 可追溯性  | 提示词、契约版本、Agent 分工、构建/测试日志、失败分析及修正原因。                              |

比较时同时说明**模型、客户端、本地/云端环境和工作流程**；它们一起变化时，只能比较“工具与流程组合”的效果，不能把差异单独归因于某个模型。跨工具 token 统计口径可能不同，费用若为 API 等价估算要明确标注。
